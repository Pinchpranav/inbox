Q: How to make the architecture support parallel conversations (multiple chats streaming at once), based on how t3code does it?
A: Move concurrency out of the WS connection into the server turn runner — add a per-sessionKey TurnRunner (queue + one in-flight turn per conversation), keep one AgentSession per key but reap idle ones, give each conversation its own isolated worktree (t3code's thread→workspace model), and switch the client from one socket-per-turn to one connection-scoped subscription channel plus per-key live state in the UI.

# 1. server/routes/chat.ts — `busy` flag is per-WS-connection, and the browser opens one socket per turn → structurally one-turn-at-a-time.

# 5. ZDR/model are global manager state today → make per-session so parallel chats can differ.
# 6. Parallel writers on the same project dir clobber each other → t3code answer = git worktree per thread (checkpoint/PR/diff all per-worktree).

Q: Explain chat.ts's startTurn design + the sidebar-mutation "source of truth" thing without jargon; and is the sidebar part even needed?
A: Demo mode is deleted (not moved) — the 4 demo data exports, mock timers, and every 'if conn!==ok' fork go away; backend-down now shows an empty-state card instead of seed data. chat.ts = a drawer (Map<sessionKey, LiveState>) per conversation, each holding its settled messages, in-progress text, status line, streaming flag, and its own open connection; startTurn(key, text) is the one function that opens/uses/closes drawer key's drawer, so switching screens no longer kills other drawers. Q: What are the 3 perspectives (t3code / our code / what to do) on decoupling UI from conversations for parallel threads?
A: t3code decouples by making the URL own the active thread and the server own per-thread sessions with one subscribe channel; our frontend is already per-key (drawer map in chat.ts) so the real blocker is server-side (per-WS `busy` flag, no per-key turn lock, global ZDR/model); the plan = server TurnRunner per session key + single subscribe-all WS + per-session worktrees.

Q: Why double-click to see a conversation (first click shows empty)? Why is the "preparing…" indicator gone after refresh?
A: Bug 1: on select, App.vue renders the drawer with messages:[] and loadHistory() is async — until fetchMessages resolves, the drawer is empty and (during streaming-guard or a race where the poll re-creates the session entry) it can show the empty-state instead of a loading state; a second click re-triggers loadHistory now that data is cached. Fix: an explicit drawer.loading flag rendered as "loading conversation…". Bug 2: "preparing…" is purely client-side drawer state (d.phase set by send()); after a refresh the drawer is new, the server turn keeps running but no browser observes it, and the 5s poll only syncs settled messages — so the indicator vanishes until message.end. Fix (part of the subscribe-all WS work): on loadHistory/connect, ask the server "is a turn running for this key?" (sessionStatus in the view payload or a status frame on subscribe) and re-derive phase/streaming from that.

Q: How does the busy flag know the assistant turn is still going (tools/thinking/text)?
A: It doesn't watch the stream — pi's session.prompt() is a promise that resolves only when the whole turn finishes, so the promise's lifetime IS the turn's lifetime; runningTurns.add(key) before the await, delete(key) in finally.
